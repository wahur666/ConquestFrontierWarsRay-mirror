## Batch 01 Conclusions

- Batch 01 is not mission scripting or UI logic. It is the strategic computer-player layer.
- `SPlayerAI.cpp` is the real implementation center; most sibling files are doctrine specializations made of weighted tables and a few decision overrides.
- The main active extension points across the strategy files are:
  - personality setup in `init`
  - build priorities in `initBuildDesires`
  - research priorities in `initResearchDesires`
  - ship mix priorities in `initShipDesires`
  - occasional readiness gates like `ReadyForMilitary`
  - occasional targeting heuristics like `MDeny::findStrategicTarget`
- The large commented blocks in many files show an older style where subclasses directly chose build packets. In the checked-in active code, most of that responsibility has already collapsed back into the shared base.
- This means the modern port should avoid a literal class-per-strategy translation where possible. A data-driven doctrine system plus a smaller set of behavioral hooks is the better fit.

## Batch 02 Conclusions

- Batch 02 is not gameplay simulation logic. It is the mission HUD/context-toolbar controller layer that decides which inspector/menu is visible for the current selection and which controls appear active.
- The common pattern across nearly every file is:
  - subscribe to toolbar/event callbacks at startup
  - every `500` ms, inspect `OBJLIST->GetSelectedList()`
  - decide whether this controller owns the panel
  - resolve a toolbar layout name from `mObjClass` and race
  - query named controls from that toolbar
  - push live object state into text/icons/button highlight states
- These files mostly do not own the final gameplay command behavior. They expose state and emit a few build/remove packets, but many click handlers are empty because the shared hot-control system or other command paths do the real work after a toolbar control becomes active.
- The real port target should therefore be a modern selection-inspector framework with derived view models for:
  - empty selection
  - single ship
  - single platform by subtype
  - fabricator/build placement
  - fleet/admiral
  - mixed group selection
  - global find/cycle toolbar actions

## Batch 03 Conclusions

- Batch 03 is mixed. Most files are genuine menu/modal surfaces, but `Menu_AdmiralBar.cpp` is closer to gameplay command infrastructure than ordinary UI.
- The batch splits into three broad roles:
  - in-mission command execution and targeting: `Menu_AdmiralBar.cpp`
  - transient communication and diplomacy overlays: `Menu_Chat.cpp`, `Menu_PlayerChat.cpp`, `Menu_Diplomacy.cpp`
  - mission/meta presentation flows: `Menu_Objectives.cpp`, `Menu_EndGame.cpp`, `Menu_netunloading.cpp`
- Several files still embed nontrivial game rules inside UI code:
  - chat cheat/debug commands in `Menu_Chat.cpp`
  - alliance/resource transfer packet assembly in `Menu_Diplomacy.cpp`
  - score formulas and campaign movie unlock flags in `Menu_EndGame.cpp`
  - objective announcement sequencing in `Menu_Objectives.cpp`
  - resign ack/retry logic in `Menu_netunloading.cpp`
- For the port, the right shape is not one-for-one menu translation. The better split is:
  - a command-targeting service for fleet/special actions
  - a chat service with recipient filtering
  - a diplomacy transaction model
  - a mission-objective presentation/announcement service
  - a post-game results/progression service
  - a network teardown status flow
- The most important warning from this batch is that the old codebase treats UI classes as orchestration shells for gameplay, network, and progression side effects. That coupling should be reduced during porting rather than preserved.
